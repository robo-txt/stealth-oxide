# Network interceptor design

Status: header sanitation and deterministic mutation policy implemented behind
the `interceptor` feature; CDP attachment and event loop remain design work.

This document defines a conservative, opt-in request interceptor for authorized
testing. It does not promise preservation of Chromium's native wire-header
ordering and must not be described as making intercepted traffic
indistinguishable from uninterrupted traffic.

The protocol authority for this design is the official
[Chrome DevTools Protocol Fetch domain](https://chromedevtools.github.io/devtools-protocol/tot/Fetch/).
The initial implementation targets the CDP types generated by
`chromiumoxide 0.9.1`.

## Goals

- Leave interception disabled unless a consumer enables a Cargo feature and
  explicitly attaches an interceptor.
- Ask Chromium to filter requests by URL, resource type, and request stage so
  unmatched requests are not paused or delivered to the Rust policy loop.
- Continue requests without overrides unless a validated policy requires a
  modification.
- Guarantee one terminal command for each request observed as paused.
- Prevent custom headers and credentials from leaking across redirect origins.
- Shut down without leaving known requests paused.
- Provide typed aggregate diagnostics and optional structured tracing.

## Non-goals

- Reconstructing or guaranteeing native HTTP/1 header order.
- Controlling HTTP/2 or HTTP/3 pseudo-header serialization.
- Modifying TLS, ALPN, QUIC, or connection-pooling behavior.
- Intercepting responses, fulfilling mock responses, or failing requests in the
  first release.
- Providing arbitrary asynchronous user callbacks in the first release.
- Concealing CDP interception from detection systems.

## Feature boundary

The proposed feature is disabled by default:

```toml
[features]
default = []
interceptor = []

[dependencies]
# Async and tracing dependencies will be added with the event-loop phase.
```

Enabling the feature only exposes the API. No interception begins until the
consumer explicitly attaches an interceptor to a page.

## Public API sketch

The public pattern type should wrap or translate to CDP's `RequestPattern`
without claiming stronger matching semantics. CDP patterns support `*` and `?`
wildcards; they are not regular expressions.

```rust,ignore
let policy = InterceptPolicy::builder()
    .request_pattern(
        InterceptPattern::builder()
            .url_pattern("https://api.example.test/*")
            .resource_type(ResourceType::Xhr)
            .build()?,
    )
    .set_header("x-test-scenario", "checkout")
    .build()?;

let interceptor = NetworkInterceptor::attach(&page, policy).await?;

// Explicit shutdown is required for a complete report.
let report = interceptor.shutdown().await?;
```

The builder rejects an empty pattern list. Calling Fetch with no patterns would
pause every request and is not an acceptable implicit fallback.

## Native filtering and request stage

Every configured pattern translates to a CDP `Fetch.RequestPattern` containing:

- `urlPattern`
- an optional `resourceType`
- `requestStage: Request`

`requestStage` belongs to each pattern; `Fetch.enable` has no global stages
field. Response-stage interception is excluded from the first release.

Native filtering avoids pausing unmatched requests and avoids sending their
pause events to the Rust policy loop. It should be described as narrowly scoped
and low-overhead, not zero-overhead: enabling Fetch and matching requests still
has browser and protocol costs.

`handleAuthRequests` remains false in the first release. Authentication support
requires a separate design and must never be enabled as a side effect of header
interception.

## Header semantics

`Fetch.continueRequest` behaves in two materially different ways:

- `headers: None` preserves the request without a header override.
- `headers: Some(...)` supplies a complete header override set.

The paused request exposes headers through a JSON object-like CDP value. Their
native HTTP/1 serialization order and HTTP/2 or HTTP/3 encoding order are not
available to the client. Rebuilding that set can therefore change wire
serialization. The crate must document this limitation at the API method that
enables header mutation.

The initial implementation supports deterministic static additions or
replacements only. It copies the exposed header set, applies validated changes,
and sends the resulting `HeaderEntry` vector. It must never claim that this
preserves native order.

Header names are compared case-insensitively. The builder rejects:

- names beginning with `:`
- `connection`
- `content-length`
- `host`
- `keep-alive`
- `proxy-authenticate`
- `proxy-authorization`
- `te`
- `trailer`
- `transfer-encoding`
- `upgrade`

`authorization`, `cookie`, and `set-cookie` are not accepted by the generic
header API. Future credential support must use a separate origin-scoped API.
Invalid configuration fails during policy construction. A runtime parsing or
mutation error continues the request unchanged; it does not fail network
traffic merely because the interceptor could not modify it.

## Redirect behavior

CDP request overrides do not extend to later redirect hops. A redirected
request is a new `requestPaused` event and may include `redirectedRequestId`.
Redirect responses are identified at response stage by a redirect status and a
`Location` header, but response-stage events are outside the initial scope.

Each new request is independently filtered by Chromium against the configured
patterns. The implementation does not copy a previous request's override into a
redirected request and does not need a redirect state map to prevent
propagation.

Diagnostics may count events with `redirectedRequestId`, but that relationship
must not authorize header reuse. A redirect target receives modifications only
if it independently matches a configured pattern.

## Single-terminal request rule

The event-loop task exclusively owns a `HashMap<RequestId, RequestState>`. No
`DashMap` or shared request-state mutex is needed.

For each pause event:

1. Insert an `Outstanding` state.
2. Compute the static policy decision without awaiting user code.
3. Remove and consume the state before sending a terminal command.
4. Send exactly one `continueRequest` command.
5. Record success or failure in aggregate diagnostics.

The first release has no arbitrary async decision callback, so it has no
decision timeout. Chromiumoxide's command/request timeout remains applicable to
the CDP command itself. If async callbacks are added later, they require a
separate bounded-decision design whose timeout consumes the outstanding state
before continuing unchanged.

`fulfillRequest`, `failRequest`, and `continueWithAuth` are deliberately absent
from the first public API. Supporting a protocol command internally does not
require exposing it prematurely.

## Event-loop failures

The loop follows a fail-open policy for modification failures:

- Header reconstruction failure: continue unchanged.
- Policy evaluation failure: continue unchanged.
- Diagnostic or tracing failure: continue unchanged.
- CDP `continueRequest` failure: record the error; do not attempt a second
  terminal command for the same request ID.

A lost CDP connection cannot be repaired by issuing more commands. It terminates
the task and returns the connection error through shutdown or the task result.

## Shutdown protocol

Dropping a Rust value cannot perform reliable asynchronous cleanup. Consumers
must call `shutdown().await` for a complete drain and report. `Drop` may signal
cancellation as a best effort but must not claim graceful shutdown.

Shutdown must not stop reading events before Fetch is disabled, because a late
matching request could otherwise become paused with no consumer. The sequence
is:

1. Mark the public handle as shutting down so it accepts no new policy changes.
2. Keep the event loop active and make every newly observed pause continue
   unchanged.
3. Resolve every known outstanding request with one unchanged continue attempt.
4. Send `Fetch.disable` while the browser handler and event loop remain active.
5. Continue handling any already-delivered pause events until the disable
   command completes.
6. Confirm the owned outstanding-state map is empty.
7. Return the aggregate report and terminate the task.

The implementation tests must determine actual Chromium behavior for requests
that race with `Fetch.disable`; the design must not assume that disabling Fetch
automatically resolves every pause.

## Diagnostics

`tracing` events use a stable target such as `stealth_oxide::interceptor`.
They may include request ID, origin, resource type, decision, elapsed time, and
error category. They must not log complete URLs containing credentials, header
values, cookies, authorization values, request bodies, or supplied credentials.

The aggregate report contains counters rather than captured traffic:

```rust,ignore
pub struct InterceptorReport {
    pub paused: u64,
    pub continued_unchanged: u64,
    pub modified: u64,
    pub redirected_requests: u64,
    pub policy_errors: u64,
    pub command_errors: u64,
    pub late_during_shutdown: u64,
}
```

## Required tests before stabilization

- Empty pattern lists are rejected.
- Every generated CDP pattern explicitly uses request stage.
- Unmatched resources are not paused.
- An unchanged decision sends `headers: None`.
- Header names are case-insensitive and replacements do not duplicate names.
- Pseudo, hop-by-hop, credential, and length headers are rejected.
- Modification errors continue unchanged.
- Redirect hops do not inherit previous modifications.
- A redirect target that independently matches a pattern receives its own
  configured modification.
- Exactly one terminal command is attempted per observed request ID.
- Shutdown resolves known and late pause events without hanging navigation.
- Dropping without shutdown does not panic.
- Logs and reports do not expose sensitive values.
- Long-running sessions do not accumulate completed request state.

Integration tests should use a repository-owned local HTTP server for redirects
and header echoing. They must not depend on third-party anti-bot services.
